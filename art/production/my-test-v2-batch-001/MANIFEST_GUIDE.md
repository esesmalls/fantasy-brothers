# Manifest与装配交付契约

## 1. 四类编号，不要混用

| 字段 | 含义 | 示例 |
|---|---|---|
| design_id | 一款造型或物件 | padded_001 |
| asset_id | 一种可选状态的逻辑资产 | padded_001_intact / padded_001_damaged |
| part_id | 该资产内部渲染片 | headgear_metal_001.back / .front |
| preset_id | 可保存重载的组合 | preset_01 |

同一头盔增加一张后片不增加asset_id数量。同款甲的完好与破损共享design_id，但使用不同asset_id并双向配对。运行时的rule_id与这些ID分开，不从名称猜测或新增战斗规则。

本模板的asset_id首先在本批内唯一。正式注册时检查全仓重名，用既有全局命名方式或“命名空间 + asset_id”保证长期唯一，并把固定映射写入runtime_asset_id。首次映射后不可随批次重排改变旧人物引用；校验器只检查本批，不证明全仓没有重名。

## 2. 文件性质

`manifest.json` 是本模板提出的**生产管理格式**，`presets.json` 是组合计划，`qa_matrix.json` 是待执行测试定义。它们不是仓库已经支持的Godot运行schema，不能直接替换catalog/modules，也不能当作my_test-v2草案加载。

所有 `null` 都表示尚未取得，所有占位part几何均为unresolved。初始参考和源图路径为空，不能仅凭asset_id或“已批准”字样调用参考编辑；实际生成前必须加载真实可用的图像参考。

基础 `baseline.bindings` 必须由执行AI读取实际工程后填写。记录本批实际提交；不要复制聊天里旧提交号或示例哈希。路径统一使用项目根目录相对路径，文件哈希为实际字节SHA-256；不要对JSON重新格式化后冒充原用户文件。

## 3. 生产阶段与尺寸权责

资产原图 → 规整与注册 → 装配器校准/组合 → 版本化装配包 → 游戏使用同包 → 一致性验收 → 用户批准。

分清四类量：

1. **源像素**：image_size_px、source_rect_px，包括透明留白。
2. **模板逻辑量**：logical_size_before_fit、position_before_fit、pivot、parent_binding。
3. **装配结果**：fit_delta、resolved_transform、裁取、各片层位、遮挡兼容关系。
4. **显示环境**：游戏单位在棋盘的位置、相机倍率和界面预览比例，不是对每件资产重做一次装配。

装配器有权确定单件资产的最终显示大小、位置与表现；my_test-v2提供共同标尺和已批准参考，不意味着所有图只能有相同数值scale。原图宽度、分辨率、透明留白不同，需要的数值变换可能相差很大。先归一化，再判断实际比例和结构，不能机械地按“缩放超过某阈值”退回。

错误朝向、衣领结构、盔口形状不能靠拉伸、实色补丁或修改全局母版掩盖。良好的局部校准应登记、复用并版本化，不按每个角色组合反复临时调一遍。

## 4. 基线几何快照

执行AI应生成 `resolved_geometry_spec`，至少覆盖：

- 实际基线提交、my_test-v2/catalog/modules/相关PNG与动作代码哈希。
- 每个槽位源矩形、逻辑尺寸、原锚点、父组、用户edits、最终局部变换与坐标约定。
- 当前bust crop及适用图层；头、头盔、武器不要默认套用衣甲盘面窗口。
- 角度单位。若草案编辑角度与动作关键帧角度不同，解析入口必须明确转换。
- 当前实际动作路径；actions缺失时记录实际默认路径来源，而不是凭空建一个actions。
- 1×在游戏里的定义、图像导入采样与相机/棋子倍率。

不要把旧legacy整头尺寸误当作modular净面头的最终尺寸。最终量由真实选中的头部模式、父级和用户变换共同决定。

## 5. 导出契约：只应用一次

本模板建议交付 **已解析最终装配包**，概念名为assembly package；实际文件名与schema由现有工程支持决定，不预设新文件已经能加载。

装配包包含：模板与包版本、资产ID/版本、每个渲染片与哈希、已解析变换、层位/遮挡、裁取、状态配对和动作版本。游戏通过同一渲染入口消费它；不能另维护一套head/armor固定坐标，也不能把draft edits再次叠到已解析结果上。

若现有代码确实需要保留“基线 + 差量”形式，则装配器和游戏必须调用同一解析器，明确标识未解析状态，禁止混用“最终值 + 再加差量”。模板字段transform_policy相应调整并补测试，不能仅改名称。

游戏允许做角色整体在棋盘的位移、当前系统已有的显示倍率与动作采样；具体允许项从现有工程确认。不会因为这条契约自动授权新增镜像朝向、光照系统或动作。

## 6. 头部装备的最小数据约束

头部装备的片数按真实遮挡需要确定。parent_binding声明跟随谁，layer_relation声明画在谁前后，二者不是同一属性。

例：一个短兜帽可能需要后片位于头后、主体包住侧脑、前缘位于发际线前；与衣领的关系另行指定。不能笼统写“整件最后画”。本批允许为此做必要的候选层位支持，不允许重写完整战斗/骨骼系统。

headgear_policy必须填：真实实体区域、片层关系、压发/露发策略、胡须/绷带兼容、衣领关系。窗口只对“该片没有材料”的区域要求透明，不禁止真正的鼻护、护颊或布料遮挡脸。

配对与兼容性按实际验证登记。未测组合不是默认通过；遇到不合身先返修，确实不兼容的组合要显式阻止或提示，不能静默换成别的资产。

## 7. 状态与证据

planned → generated → normalized → registered → qa_pass → game_verified → user_approved。

needs_revision / blocked为可进入的异常状态。qa_pass只代表适用装配项通过，game_verified还必须完成游戏一致性检查；user_approved须有用户真实指令/批注来源。

每个PASS的证据绑定asset哈希、装配版本和测试场景。文件或装配变更后将受影响用例重置NOT_RUN，旧截图保留历史但不当成本次证明。

建议证据使用对象：{"check":"assembly_visual", "path":"art/production/my-test-v2-batch-001/previews/实际文件.png", "tested_revision":"实际装配版本"}。实际游戏结果还记录代码/导出包版本。没有运行就写NOT_RUN，不以计划命令或脚本存在替代执行。

## 8. 轻量验证器的范围

`tools/validate_batch.py` 可检查JSON结构、计数、稳定ID引用、配对、8套覆盖、测试引用与所声明阶段的必填内容；在组装/游戏门槛模式下验证相关文件存在与登记哈希。

它**不生成图片，不解析Godot渲染，不自动判断alpha是否正确，不检查头盔是否好看，也不能证明人类实际执行了填写PASS的检查**。PASS数据仍须真实运行证据支撑。它不修改任何状态，也不写仓库。
