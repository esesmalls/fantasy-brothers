# 美术生产方式选型（待用户确认）

日期：2026-09-19。基线：0.1.5.1 / Godot 4.7.2 stable。

## 本轮边界

用户要求先比较资产制作方法并解释选择，同意后才展开详细美术方案及四步功能开发。本轮仅做工程审查与官方资料核验，没有生成资产、安装工具、购买服务、修改游戏或启动四步实现。下述推荐不等于已经批准。

目标是覆盖当前游玩框架的地图、战场、人物、装备、物件、图标、文本排版和界面边框；参考 Battle Brothers 的中世纪手绘质感、脸部可读性与模块组合方法，制作本项目自己的资产。完整清单与数量留待方法确认后编制。

## 推荐方式

采用 **模块化手绘 2D + OpenAI 图像生成/参考编辑 + 分层修整与定位校准 + Godot 组合、动画和真实 UI 控件**。以固定朝向、面容和上身装备清楚可辨的半身棋子为优先样板方向，最终比例仍需用户评审；旧文档的完整身体剪影也是提案，不能视为已批准标准。

| 方法 | 建议角色 | 理由与限制 |
| --- | --- | --- |
| OpenAI 图像生成与参考编辑 | 主美术生成入口：风格母版、脸部与装备部件、材质、地标、状态变体 | 支持参考图编辑和透明输出；适合探索手绘视觉。不能保证跨次生成的精确位置、人物一致性和文字排版，输出须修整、配准与游戏内验收。 |
| 分层修整、统一画布和定位清单 | 必需的资产加工环节 | 同一身体母版统一头颈、肩、手握点、尺寸、层序和遮挡；保留可编辑的独立部件。生成一张漂亮完整人物图不能替代可换装资源。具体编辑工具在样板阶段按可用性选择，不预设用户承担大量手工修图。 |
| Godot 2D | 最终装配与表现系统 | 沿用当前规则及战场坐标；组合贴图、映射真实伤损、驱动动画/特效与 UI。图标、选中轮廓和提示等适合继续用精确程序绘制，人物及材质则引入绘制资产。 |
| SpriteCook MCP | 可选辅助，当前不接入 | 官方支持非像素模式、参考编辑、透明处理、帧对齐、切图、地块和 UI/Godot 导出。未找到保证人物/装备语义分层、跨动作共用锚点或同装备破损系列一致性的专用机制。其便利主要是加工与导出流程，不能代替本项目的模块规范。 |
| 完整 3D 建模后转 2D | 当前不选为主流程 | 属于本项目成本判断：会增加建模、绑定、材质与动作工作；当前固定朝向半身换装更适合直接 2D。未来若确需多方向或复杂动作，再对独立资产评估。 |

## 必须由制作方法保证的效果

- **人物身份稳定且可区分**：脸型、五官、发型、胡须等组合要保持统一光照和比例；外观选择按稳定 ID 保存，并检查在役队伍的可见组合重复。受伤/表情变化保持同一张脸，不靠重复生成完整人物碰运气；有限素材库不承诺无限绝不重复。
- **装备真正穿戴**：以批准的身体母版生成可替换层，控制领口、肩线、握点及头发/装备遮挡。兼容体型使用明确模板，不能只把任意装备图片缩放贴到身体上。营地与战场复用同一外观来源。
- **同装备的状态连续**：受损版从同一完好母版衍生，保留造型、材质和装饰身份；明显破损做专用变体，通用血迹/污渍可用局部叠层。显示状态由实际规则数据驱动。
- **地图与战场可以组合**：地面、边缘过渡、装饰、互动对象、油水、火焰/蒸汽分层；避免把整片战场烘成一张不可互动背景。保留现有元素与受击反馈。装饰不能暗示尚不存在的地形规则。
- **界面美术不牺牲信息**：手绘木、金属、皮革/纸张用于可伸缩边框与局部装饰；中文、数字、血条和按钮继续用真实控件绘制。保留战场优先、默认图标色条、Alt 详细信息。
- **动画成本可扩展**：角色先使用合成部件的位移、倾斜、受击及局部动作；需要逐帧的特效或生物动作单独做统一画布动画，不为每种脸与装备组合重画整套角色动作。

## 现有工程适配证据

审查范围：`character_portrait.gd`、`battle_board.gd`、`world_map.gd`、`tactical_glyph.gd`、装备规则/数据和营地人物/军需页面。

- 当前主要是程序绘图，人物共享 96×88 逻辑画布；绘制有层序，但没有正式贴图清单、手握点或遮挡元数据。现有共享人物接口和战场层序可继续使用，不需要改换引擎或重写六边格规则。
- 护甲已有实例耐久，可以驱动完好与多档受损资产；生命比例可以驱动一般伤势/痛苦表情。独立头盔、副手、披风、武器磨损和具体身体伤残尚未实现，不能仅靠美术伪装这些规则已经存在。
- 当前身份外观由 ID 哈希派生，正式资产库需保存稳定外观部件选择，避免日后增加素材导致旧人物换脸。
- 新轮廓接入后需要复核鼠标命中、物件遮挡和当前行动者可读性；这些属于后续样板验收，不宣称本次已经通过新资产实测。

## 成本与后续决定

成本优势来自部件复用：同一件甲可搭配多个身份，并共享损伤系列；同一 UI 边框与地块材质可复用。先锁定风格母版与接口，再扩充覆盖面，避免大量独立出图后重新绘制。按“验收可用部件及修整时间”评价成本，不按生成图片数或宣传额度判断便宜。

SpriteCook 是另一个服务层，是否节省总成本尚未实测；当前没有可调用的 SpriteCook 接入。用户确认后，如确需比较，只做受控样板评估，不预先购买订阅或把工程绑定到该服务。本文不承诺具体费用、产量或期限。

用户同意方法后，再编制覆盖当前框架的完整资产清单、视觉标准、状态/组合验收和 AI 分工，并与 [四步批次](16-next-four-steps.md) 合并安排：招聘后勤→差异契约→出战替补部署→伤势/伤残/性格样本。当前四步仍未开始实现。
